### OpenAPI spec — committed and CI-verified, not hand-written

Generated for real, not guessed: brought up Postgres 16, Redis, and Kafka via
`docker-compose` (`postgres`, `redis`, `kafka` services — the `minio`
service, gated behind its own `profiles: [minio]`, was left untouched and
never started), ran the actual API module with `mvn spring-boot:run` against
them (`DB_*`, `WEBHOOK_ENCRYPTION_KEY/SALT`, `JWT_SECRET`, `MANAGEMENT_PORT`
env vars — `SWAGGER_ENABLED` isn't required for `/v3/api-docs.yaml` itself,
only for the Swagger UI page), and curled the live
`http://localhost:8099/v3/api-docs.yaml` once all 54 Flyway migrations had
run and the app reported `Started WebhookPlatformApiApplication`. Fixed the
`servers[0].url` from the local dev port to `http://localhost:8080` (the
documented default) before committing as `openapi.yaml` at the repo root.

Result: **9,996 lines, 128 paths, 40 tags** — every controller-declared tag
present (Events, Endpoints, Subscriptions, Deliveries, Organizations,
Projects, Workflows, Rules, Schema Registry, Billing, Tunnels, etc.), springdoc
2.3.0. All containers (`webhook-postgres`, `webhook-redis`, `webhook-kafka`)
and the `mvn spring-boot:run` process were torn down afterward
(`docker-compose --profile embedded-db down`, `kill`) — nothing left running
for sibling worktree agents to collide with.

**CI wiring** (`.github/workflows/ci.yml`, `docker-compose-smoke` job — the
job that already boots the real `docker-compose.pull.yml` stack on every
push): added `SWAGGER_ENABLED: "true"` to the stack's env, then a new
"Export OpenAPI spec and check for drift" step that curls the running API's
`/v3/api-docs.yaml` and `diff -u`s it against the committed `openapi.yaml`,
failing the build on drift with a message telling the fixer exactly how to
regenerate. The generated spec is also uploaded as a build artifact
(`openapi-spec`) for visibility. This is a drift *gate*, not an auto-commit —
CI has no write access back to the branch, so a human/agent regenerates and
commits `openapi.yaml` when the diff step fails, same pattern as the existing
coverage-badge-is-manual note in the Coverage section.

**Drive-by fix required to get here:** `webhook-platform-coverage-report/pom.xml`
still pointed its `<parent><version>` at `1.0.0-SNAPSHOT` (missed by P1-16's
version reconciliation, since that module was added later by P1-28) — this
broke every full-reactor Maven invocation (`Could not find artifact
com.webhook.platform:webhook-platform-cli:jar:1.0.0-SNAPSHOT`), including
this task's own license-report tooling below. Fixed to `2.2.1` to match every
other module's parent reference (verified: `grep -rl "1.0.0-SNAPSHOT"
--include=pom.xml .` now returns nothing). Confirmed harmless:
`mvn compile` across the full 5-module reactor succeeds cleanly after the
fix.
